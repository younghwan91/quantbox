# G9: 라이브 포트폴리오 필터 백테스트 이식

- **일자**: 2026-08-10
- **기준 커밋**: `12b1e44`
- **브랜치**: `feature/mega-v2-phase5`
- **범위**: Mega Refactor v2 — Phase 5.3 (G9)

## 문제

라이브는 진입 직전 `RiskGuard`(`execution/risk_guard.py`)로 세 가지를 더 본다:

| 필터 | 라이브 규칙 | 백테스트 |
|---|---|---|
| 방향 분산 | 같은 방향 `max_same_direction`(=5) 이상이면 차단 | ❌ 없음 |
| BTC 트렌드 게이트 | BTC < MA50(15m)이면 LONG 차단 | ❌ 없음 |
| 일손실 차단기 | 당일 실현손실 > 잔고 × `daily_loss_limit_pct` → 신규 진입 차단 | ❌ 없음 |

`portfolio_sim`은 슬롯 상한과 동일 심볼 중복만 봤다. 나머지 셋이 없다는 건 백테스트가
**라이브라면 거절했을 트레이드를 계속 세고 있었다**는 뜻이다.

부수적으로, sim이 방향(`dirs`)을 계산해 놓고 버리고 있어서 방향 기반 필터는 적용 자체가
불가능했다 (`_dr = sim_drive(...)`).

## 구현

- `portfolio_sim_with_details`에 필터 3종 추가. `portfolio_sim`은 이제 여기에 **위임**한다
  (중복 루프 하나 제거 — 슬롯 로직 사본이 둘이었다).
- 정렬은 방향 배열과 함께 수행한다. 따로 정렬하면 인덱스가 어긋나 필터가 조용히 엉뚱한
  방향을 본다.
- 일손실 차단기는 **이미 청산된** 손익만 센다. 진입 순서로 순회하므로 아직 안 끝난
  트레이드의 손실을 미리 반영하면 라이브가 허용했을 진입을 부당하게 막는다.
- `run_ma_cluster` / `run_ma_cluster_live`에 `return_directions=True` 추가.
- **전부 opt-in.** 기본값을 켜면 기존 리서치 baseline이 전부 무효화되고, `portfolio_sim`은
  골든·파리티 테스트가 걸린 공용 경로다.

## 해석

### BTC 게이트가 지배적이다 — 진입의 23%를 차단한다

1,652 → 1,271. **381건(23.1%)이 라이브에서는 나가지 않았을 진입**이다. 남은 트레이드의
질은 올라간다(PF 2.078→2.193, WR 68.0→69.5%). 하지만 건수가 줄어 **연수익은
14.3% → 11.4%로 내려간다.** MaxDD가 그대로라 Calmar는 7.3 → 5.7로 오히려 악화된다.

G8과 같은 종류의 결론이다: 필터를 넣으면 성과가 좋아지는 게 아니라, **백테스트가
과대평가하고 있었다는 사실이 드러난다.**

### 방향 분산은 사실상 무효 (8건, 0.5%)

`max_same_direction=5`에 걸리려면 동시 보유가 5건을 넘어야 하는데, 실측 슬롯 가동률이
2.12%(평균 동시보유 0.212/10)라 도달하지 않는다. 필터가 없어서가 아니라 **신호가
희소해서** 안 걸린다.

### 일손실 차단기는 한 번도 발동하지 않았다 (0건)

등분 슬롯 사이징에서 트레이드 1건의 자기자본 영향은 `pnl / 10`이다. 하루 실현손실이
`daily_loss_limit_pct`에 도달한 날이 6년간 없다. 이 차단기는 백테스트 분포에서는
사문(死文)이고, 실제로는 라이브의 꼬리위험 보호 장치로만 의미가 있다.

## 남은 것

BTC 게이트의 백테스트 구현은 **정렬된 15m 타임라인의 BTC 종가**를 쓴다. 라이브는 매
사이클 최신 15m 종가로 MA50을 계산하므로 의미가 같지만, 심볼별 `_offset`이 어긋난
구간에서는 BTC 시리즈 앞부분이 NaN이라 게이트가 통과 처리된다(라이브도 데이터 부족 시
`compute_btc_gate`가 None을 반환해 통과시킨다 — 동일 거동).
